## Startup root-cause evidence and limits

The exact reported live error was **not reproduced**. The strongest confirmed code-level issue was that the previous auth provider trusted a local `getSession()` result or auth event immediately, without verifying that its user still existed remotely. It could then run profile/settings queries under an unusable session. This is a plausible explanation for refresh-dependent startup, not a confirmed remote root cause.

The literal global “We hit a snag” screen is reached only when `loadUserSetupWithRetry` rejects. That function runs essential `user_settings` and `profiles` reads in parallel. Development diagnostics now identify which read failed and include the available Supabase code, status, message, details and hint. No session object, credentials or records are intentionally logged.

The revised sequence is: initialize the existing singleton Supabase client; subscribe before `getSession`; ignore a stale session result after an auth event; defer SDK validation outside the auth callback lock; validate the current account with `getUser`; retry transient validation failures within bounds; locally clear deleted/invalid sessions; then read essential account setup with its existing bounded backoff. Permission/schema failures stop rather than retrying indefinitely. Prior-account and disposed Strict Mode requests cannot publish state. Token refresh for an already-ready account does not unmount its form.

Starter libraries are installed by existing database signup triggers, not by new startup writes. Missing/failed feature-library reads cannot trigger the global bootstrap error. Lazy feature errors are contained locally. Service-worker v5 excludes cross-origin/Supabase/auth/API requests and caches only navigation or known static assets without query strings; it does not cache account responses.

Tests simulate deferred startup, stale `getSession`, account switching during validation, deleted users, transient 503 recovery, Strict Mode disposal and token refresh. They establish code-level recovery without manual refresh, but cannot prove that the unobserved remote failure is fixed. Capture the operation-specific development diagnostic during authenticated QA if it recurs.
