## Confirmed defects versus unconfirmed production causes

- The old rank renderer appended an equals marker to competition ranks. The final implementation deliberately uses **ordinal numbering**: equal scores are ordered by trimmed, case-normalized display name, then stable membership ID. Rank is numeric; CSS does not conceal data errors. Step counts are not sent to leaderboards; no missing step value becomes a competitive zero, and the summary RPC exposes aggregates only.
- The handed-over code compared some performed/creation timestamps lexically. Equivalent timestamps with different offsets could reverse PR chronology. History and PR ordering now parse timestamps; set order and stable ID break remaining ties.
- Assisted PR calculation accepted a missing weight as a reps-only baseline. Missing assistance is now excluded from that pipeline and the group-summary equivalent. Existing load-mode database enforcement already requires nonnegative weight for Weight + Reps; 011 restricts lower-is-better to that mode.
- Explicit reps-only metadata was not checked in weighted milestone eligibility. Legacy rows with weights could enter Rep Weight. The relationship query now includes `load_mode` and the filter respects it. Explicit load mode also takes precedence over the legacy name fallback when constructing entry forms.
- The incoming auth code gave every validation failure a connection message, did not retry initial session reads, and allowed never-settling requests to hold loading forever. It now classifies permanent failures, bounds each startup wait at 15 seconds, and retries transient session reads/validation up to three attempts with 250/500 ms backoff. Companion reads use four attempts with 150/300/600 ms backoff. Deadline expiry does not cancel an SDK operation; late publication is suppressed, and late promise rejections are handled. Existing subscription generation guards and account subscriber cleanup remain in place.
- The incoming migration renamed normalized existing starter matches. It now preserves user spelling and updates only the documented catalog metadata. Reapplication avoids no-op direction/primary-group updates.
- Cardio Progress originally used a single unpaged query, which could truncate larger histories and step totals at the server row limit. It now fetches stable 500-row pages and rejects partial totals on a later-page failure. The shared Steps Y-axis controls were also disconnected from the chart; they now apply to the aggregated values.
- Announcement dismissal previously relied on React state to prevent duplicate calls. A synchronous ref now blocks a second invocation before rerender; failure keeps the dialog open and retryable.

**Not established:** the precise cause of the reported production “We hit a snag”, daily-looking muscle graph screenshots, or one-point Rep Weight symptom. The available worktree already contained core auth-generation guards and weighted milestone logic. Do not attribute production symptoms to an assumed missing trigger, missing row, auth deadlock, or cached PWA shell without evidence. Weekly/monthly bucket shape, eligibility, diagnostics, bounded waits and race tests are local corrections/defensive improvements, not proof of a live root cause.

## Startup audit

The Supabase client is a module singleton. Auth subscription registers before `getSession`; an auth event supersedes its pending result. Validation is deferred outside the SDK callback/lock. Repeated same-account pending events share validation and retain the newest session; token refresh of a ready account does not rerun account setup. Sign-out/account change invalidates old publications. Strict Mode cleanup suppresses obsolete listeners/results; companion reads share only in-flight work per client/account. App screens are gated on matching authenticated identity plus successful profile/settings bootstrap. Recovery is handled by AuthProvider before normal authenticated screens. Schema/RLS/relationship errors stop retrying and retain accurate errors; exhausted transient failures offer Retry and online/resume recovery. No retries are scheduled after a successful bootstrap.

The 001 account trigger creates profile/settings; starter triggers follow. Missing companion responses are retried, never treated as completed onboarding or silently repaired. Persistent absence requires operator investigation. No account-row repair RPC is added to 011.

The service worker uses a new shell cache generation, rejects non-GET/cross-origin/auth/rest/api/functions/storage requests and query-bearing routes, and refuses HTML responses as asset-cache entries. Stale chunk recovery is bounded; lazy feature failures expose Retry. Diagnostics contain only fixed operation labels, classification, sanitized code/status in development—no tokens, headers, identities or records.

## Migration scope and narrow catalog rules

File: `supabase/migrations/202609220011_cardio_steps_and_assisted_progression.sql`.

1. Adds nullable integer `cardio_sessions.step_count`, no default, positive-or-null check. Existing non-null partial-state step values must already be valid and are retained.
2. Adds text `exercises.progression_direction`, defaults existing non-catalog exercises to `higher_is_better`, validates allowed directions and compatible load/tracking modes.
3. Installs private Assisted Dip, Assisted Pull Up and Assisted Chin Up for every existing account and through a future-user trigger ordered after existing starters. Matching lowercases, removes non-alphanumeric characters, and removes one trailing plural `s`. Thus “Assisted Pull-Up” / “Assisted Pull Ups” match; “Custom Assisted Pull Up” does not. More than one equivalent or an incompatible tracking/load mode aborts the **whole transaction** without deleting/merging records.
4. For exactly one compatible assisted equivalent, changes only progression direction; preserves ID, spelling, archived state, compound flag, existing primary group (except Dip rule), and all existing group/tags. Adds its primary group assignment and catalog muscle tag if missing. Existing canonical assisted history will be **interpreted as assistance** when badges are recalculated, but stored values/dates are untouched. Review the preflight count of matches with history to approve this narrow semantic rule; if the name was used for added weight, stop and resolve deliberately outside this migration. Do not blindly apply it.
5. Canonical Dip(s), Weighted Dip(s), Assisted Dip(s), including spacing/punctuation variants, get Arms primary plus Arms/Triceps assignments. Secondary tags/groups remain.
6. Extends owner-scoped exercise save and aggregate-only group PR summary; keeps higher-is-better PR behavior, membership/privacy checks, and unit comparison grid. The catalog helpers are unavailable to anon/authenticated/PUBLIC. Security-definer functions use an empty search path and schema-qualified application relations/functions; built-ins resolve through implicit `pg_catalog`.
7. Keeps existing indexes, ownership constraints, RLS and grants. No step index is needed for the existing date/location/activity queries. No redundant release schema: migration 010 supports arbitrary stable release IDs.

There are no performance-value updates or deletions, no edits to 001–010, and no new publicly callable companion-row repair. Unexpected column types/generated columns, invalid partial data, disabled required RLS, or catalog collisions fail closed. Arbitrary unknown partial schema is not automatically rewritten.
